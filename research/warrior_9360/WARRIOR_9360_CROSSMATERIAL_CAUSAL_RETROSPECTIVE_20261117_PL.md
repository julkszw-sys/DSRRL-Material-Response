# Retrospektywa: Warrior / Standard Helm 9360 jako ujawnienie błędów **wspólnych dla wielu materiałów**

**Rekonstrukcja 17 listopada 2026, z Supabase + repo GitHub.** Nie jest nowym buildem, patchem ani pixel PASS. DSR host, PTDE target. Repo ref history: PR #514, #515, #518. Zamrożony V359-RC1 niezmieniony.

## Wniosek zasadniczy

Warrior / Standard Helm HD_M_9360 *nie* stanowił wyłącznie błędu pojedynczego C_Metal. Był dobrym przypadkiem testowym, który sprowokował identyfikację **kilku niezależnych blokad upstream**. Najmocniej udowodniona wspólna naprawa zasobów to V13 callback loader: 34 brakujące pary Diffuse na 32 modelach pancerzy + jeden Normal triple (HD_M_9360). Kolejny **wspólny** operator routingu: niekompletna baza surowych SHA MTD — 29 brakujących tras, później rozszerzenie do 33/35 source-resolvable — i oddzielny cache shaderów, który potrafił utrwalić stary negatywny wynik. Nie wszystkie przyczynowo odpowiadają za widoczną poprawę; rzeczywiste matched pixel A/B nie istnieją w dokumentach.

## Co jest potwierdzone, a czego nie wolno dopowiadać

**CONFIRMED:** brakujące 34/1 source mappings; konkretna V12-only callback przyczyna i jej zamiana; rzeczywisty runtime loaded Diffuse/Normal/Spec po fixie, V13 18/18 ready; brak C_Metal raw SHA i późniejszy parser→selector→identity→prepared; BND3 registry 33/35; shader TLS negative-cache source bug; nieudowodnione 38-row / V296 gates w source i ich usunięcie.

**WNIOSKOWANIE:** użytkownik wspomina widoczną poprawę wielu materiałów. Z dokumentów widać wiele *kandydatów* przyczyn szerokiego efektu (callback + BND identity + cache + gate removal), ale bez matched-scene A/B i pixel captures nie można przypisać użytkowego rezultatu jednemu commitowi ani ogłosić pełnej PTDE equivalence.

**REJECTED/PROTECTED:** nie odtwarzać 38-row powszechnego veto, globalnego epoch bump, V296 cross-operator veto i nieautoryzowanego globalnego MTD basename remap. Zachować source exact owner/slot/MTD, logical SRV identity, real shader consumer, GPU state, PTDE target. Route229 C_Metal nie staje się P_Metal route345 przez samą obecność Diffuse/Normal.

## Ważna analogia dla dzisiejszego selektora LightBank RX34

Dzisiejszy przypadek może powtarzać **strukturę błędu upstream**: widzimy RX34 + Source1 + row30/31, ale zaczynamy od zbyt późnych gate lub utożsamiamy rozpoznany asset z gotowym przypisaniem właściciela. W 9360 skuteczna kolejność była: `source corpus → exact owner+raw MTD → logical texture target → actual callback / shader registration → specific receiver → draw issue → downstream PTDE pixel`.

Dla obecnego RX34 trzeba więc najpierw ustalić **pierwszy rozchodzący się producer/consumer semantic key**: `FrpgModel registration handle → opcode0x804C selector packet → addressed FrpgModelDrawEntity handle / embedded DrawParam → issued RX34 material/shader`, nie zmieniać row30↔31 bez owner-join i nie dokładać arbitralnego globalnego veto. V418 Fg-parent-only gate nie obejmuje 299/299 obserwowanych class2 Source1 RX34, analogicznie do dawnego V12-only target admission. Ale V418 był dotąd obserwatorem — jego niepowodzenie nie oznacza automatycznie błędu faktycznej selekcji.
